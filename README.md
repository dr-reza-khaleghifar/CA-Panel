# گواهی دیجیتال ایران | Iran CA Center

پنل سازمانی صدور و مدیریت گواهی‌های دیجیتال با طراحی **کاملاً دارک (Enterprise)**، رابط فارسی RTL، اعتبارسنجی مالکیت دامنه و CA اختصاصی. نام مخزن و دستورهای فنی پروژه همچنان **CA-Panel** باقی مانده‌اند.

پنل سبک صدور گواهی TLS با CA اختصاصی، رابط فارسی و استقرار Docker. کاربر دامنه را وارد می‌کند، مالکیت DNS را با TXT ثابت می‌کند و پس از تأیید DNS، **سرور کلید خصوصی و CSR را به‌صورت خودکار ایجاد می‌کند** و گواهی را امضا می‌کند و یک **گواهی با اعتبار پیش‌فرض ۳۰روزه (قابل تنظیم در `.env`)** تحویل می‌دهد؛ فایل‌های گواهی و کلید در یک ZIP دانلود می‌شوند. کلید خصوصی به شکل موقت در حافظه سرور ایجاد می‌شود و تنها با لینک محرمانه یک‌بارمصرف (پیش‌فرض ۱۰ دقیقه اعتبار) در قالب ZIP تحویل داده می‌شود؛ در SQLite یا روی دیسک ذخیره نمی‌شود.

> **مهم:** این پروژه یک **Private CA** است. گواهی‌های صادرشده به‌صورت پیش‌فرض نزد Chrome/Firefox/Safari/سیستم‌عامل‌های عمومی trusted نیستند. نصب ریشه CA در کلاینت‌ها اقدامی حساس و مدیریتی است. اگر به SSL معتبر عمومی برای بازدیدکنندگان اینترنت نیاز دارید، از یک CA مورد اعتماد عمومی مثل Let's Encrypt استفاده کنید. گواهی HTTPS خود **پنل** در حالت public توسط Caddy/ACME تأمین می‌شود و ربطی به گواهی‌های صادرشده از CA خصوصی ندارد.

## راهنمای HTTP برای مرورگرهایی که هنوز به Root CA اعتماد ندارند

اگر مرورگر به HTTPS خصوصی سامانه اعتماد نمی‌کند، **صفحه راهنمای عمومی** را به‌صورت دستی باز کنید:

**http://ca1.iravand.ir/**

این آدرس فقط راهنمای نصب Root CA و فایل **گواهی عمومی ریشه** را نمایش می‌دهد. برای احراز هویت و صدور گواهی هیچ مسیر API، فرم ورود یا دانلود خصوصی روی HTTP وجود ندارد؛ پس از نصب و **بررسی مستقل اثر انگشت SHA-256 گواهی از یک کانال مورد اعتماد**، باید به `https://ca1.iravand.ir/login` بازگردید.

مرورگرها پس از هشدار اعتبارسنجی گواهی الزاماً و خودکار به HTTP منتقل نمی‌شوند؛ برخی به دلیل HTTPS-Only یا HSTS اصلاً HTTP را باز نمی‌کنند. در این شرایط Root را از یک کانال مدیریتی مستقل و مورد اعتماد دریافت کنید. در محیط‌های مدیریت‌نشده نصب گواهی ریشه نیازمند موافقت کاربر/مدیر دستگاه است.

برای فعال‌سازی HTTP صفحه راهنما، `bash install.sh --private-https` را بعد از `git pull` اجرا کنید؛ این حالت پورت ۸۰ را فقط برای محتوای آموزشی و پورت ۴۴۳ را برای پنل امن استفاده می‌کند. توجه کنید اگر سرویس دیگری پورت ۸۰ را اشغال کرده باشد، نیاز به رفع تداخل وجود دارد. [مستندات استقرار و سیاست امنیت HTTP](docs/HTTP_TRUST_ONBOARDING.md).

## امنیت صدور و ورود دومرحله‌ای مدیر — الزامی در نسخه جدید

**تغییر مهم در نسخه فعلی:** مسیرهای ایجاد درخواست، تأیید DNS، امضای گواهی و دریافت بسته خصوصی ZIP بدون ورود مدیر بسته‌اند. برای استفاده از سرور Ubuntu موجود، پس از محدودکردن پورت ۴۴۳ در فایروال شبکه، یک بار اجرا کنید:

```bash
cd ~/CA-Panel
git pull
python3 scripts/setup_admin.py
bash install.sh --private-https
```

اسکریپت مدیریتی، رمز قوی (۱۶ کاراکتر یا بیشتر)، کلید دومرحله‌ای TOTP و لیست دامنه‌های مجاز را با دسترسی محدود تنظیم می‌کند؛ حساب ورود `admin` است. بدون این مرحله صدور گواهی به‌صورت **fail-closed** غیرفعال می‌ماند. در صورت نیاز به تغییر رمز/کلید MFA، دستور `python3 scripts/setup_admin.py --rotate` را اجرا کنید و سپس سرویس را دوباره نصب کنید. **هرگز کد MFA، رمز، .env و کلیدهای CA را در چت یا GitHub قرار ندهید.**

در این نسخه سیاست `CERT_ALLOWED_DOMAINS` دامنه‌های مجاز را محدود می‌کند. برای صدور روی **همه دامنه‌های عمومی معتبر** می‌توانید در راه‌اندازی مدیر `*` را وارد و تأیید صریح کنید، یا `CERT_ALLOW_ANY_DOMAIN=1` را در `.env` تنظیم کنید. حالت پیش‌فرض محدود است و احراز هویت **جایگزین TXT DNS نیست**؛ تأیید DNS همچنان اجباری است. تست‌های امنیتی، `pip-audit` و Bandit در CI افزوده شده‌اند. این پروژه در حال حاضر فقط یک مدیر با MFA دارد؛ SSO/RBAC چندکاربره، HSM، CRL/OCSP و تست نفوذ مستقل هنوز وجود ندارند. [راهنمای کامل ارتقای امن و ریسک‌های باقی‌مانده](docs/SECURITY_HARDENING.md).

## اعمال برند و رابط جدید روی Ubuntu موجود

آخرین نسخه رابط کاربری از GitHub با نام **گواهی دیجیتال ایران | Iran CA Center** و تم ثابت تیره ارائه می‌شود. **تغییر نام نمایشی گواهی‌های CA را بازتولید نمی‌کند** و نباید `secrets/`، کلیدهای موجود یا پایگاه داده را حذف کنید.

```bash
cd ~/CA-Panel
git pull
# فقط مقدار نمایشی سامانه، نه کلیدهای CA. پیش از تغییر از .env نسخه پشتیبان امن تهیه کنید.
sed -i "s/^CA_DISPLAY_NAME=.*/CA_DISPLAY_NAME='گواهی دیجیتال ایران'/" .env
sed -i "s/^CA_ORGANIZATION=.*/CA_ORGANIZATION='Iran CA Center'/" .env
chmod 600 .env
python3 scripts/setup_admin.py
bash install.sh --private-https
```

آدرس: `https://ca1.iravand.ir`؛ مرورگرهایی که Root CA خصوصی پردیس را نصب نکرده‌اند، همچنان اخطار عدم اعتماد نمایش می‌دهند. نسخه جدید دارای ورود مدیریتی دومرحله‌ای است، اما محدودیت شبکه و ممیزی مستقل همچنان لازم است.

رابط شامل نمای کلی با داده واقعی API، وضعیت HTTPS بر اساس اتصال مرورگر، مراحل صدور، کپی DNS/Fingerprint، دانلود محرمانه یک‌بارمصرف، ناوبری موبایل و راهنمای اعتماد است. **داشبورد مدیریت کلیدها، تمدید خودکار زمان‌بندی‌شده، مانیتورینگ پورت ۴۴۳ از کلاینت و آمار سازمانی ساختگی به پروژه اضافه نشده‌اند.** اطلاعات Root/Issuer از گواهی واقعی بارگذاری می‌شود. اگر `.env` قبلاً هویت نمایشی دیگری دارد، `git pull` به‌تنهایی آن را عوض نمی‌کند و باید مطابق دستور بالا مقدارهای نمایشی را تنظیم کنید.

## بهبود تجربه کاربری (نسخه دوم رابط Enterprise)

در این بازنگری تمرکز بر سرعت و وضوح فرایند صدور است، نه فقط ظاهر:

- فرم صدور گواهی درست پس از نمای کلی قرار دارد؛ بخش معرفی ثانویه به پایین صفحه منتقل شده است.
- نوار پیشرفت، عنوان مرحله و فوکوس صفحه‌کلید هنگام تغییر مرحله به‌روز می‌شوند.
- پیش‌نمایش دامنه، بازخورد مشخص DNS، بارگذاری قابل مشاهده و تلاش دوباره در صورت اختلال صدور اضافه شده‌اند.
- لینک یک‌بارمصرف ZIP در صورت نزدیک‌شدن به پایان مهلت یا پس از انقضا، هشدار زمینه‌ای نمایش می‌دهد؛ هیچ URL محرمانه‌ای در `localStorage` ذخیره نمی‌شود.
- دانلود گواهی **عمومی** Root به همراه یادآوری بررسی مستقل اثر انگشت ارائه می‌شود؛ دانلود Root به‌تنهایی به معنی قابل اعتمادشدن آن نیست.
- دسترسی سریع صفحه‌کلید به فرم، نگه‌داشتن فوکوس در منوی موبایل و طراحی واکنش‌گرا بهبود یافته‌اند.

این ویژگی‌ها تغییری در الزامات DNS و کنترل‌های backend ندارند؛ هیچ ادعای ساختگی درباره سلامت پورت ۴۴۳، قابل‌اعتمادبودن عمومی CA یا موفقیت قطعی دانلود فایل مطرح نمی‌شود.

## نصب کاملاً تازه Ubuntu با Root و Issuing CA جدید

اگر **هیچ کلید یا گواهی قبلی ندارید** و می‌خواهید با هویت تازه «پردیس» از صفر شروع کنید، مراحل [نصب صفر تا صد Ubuntu و ساخت CA جدید](docs/UBUNTU_FRESH_CA.md) را دنبال کنید. نصاب `bash install.sh --init-ca` نام‌ها، اعتبار، اندازه کلیدها و نام فایل‌های Root/Issuer را از `.env` می‌خواند؛ پس از ساخت، **کلید خصوصی Root را به محل امن آفلاین انتقال دهید** و تنها سپس سرویس را روی localhost و HTTPS ۴۴۳ بالا بیاورید. Root جدید باید به مخزن اعتماد مرورگر اختصاصی شما نیز اضافه شود.

## نصب از صفر روی Ubuntu (گواهی اختصاصی CA و پورت ۴۴۳)

برای مهاجرت از Mac به یک Ubuntu تازه **بدون تغییر Root CA مورد اعتماد مرورگر**، از راهنمای مرحله‌به‌مرحله [نصب Ubuntu و فعال‌سازی HTTPS خصوصی](docs/UBUNTU_INSTALL.md) استفاده کنید. این راهنما نصب Docker، انتقال امن فایل‌های Issuing CA، تنظیم .env، صدور گواهی وب‌سایت، Caddy روی ۴۴۳ و آزمون با Root CA را پوشش می‌دهد. **کلید خصوصی آفلاین Root را روی Ubuntu منتقل نکنید.**

## امکانات MVP

- رابط فارسی RTL با حساب مدیریتی دومرحله‌ای، نشست امن، محافظت CSRF و محدودیت دامنه‌های صدور
- ثبت دامنه/URL و اثبات مالکیت با DNS TXT؛ چالش تصادفی و انقضای یک‌ساعته
- بررسی مجدد DNS درست لحظه امضا؛ محدودسازی نرخ ثبت و تلاش برای تأیید
- امضای CSR (RSA >= 2048 یا P-256/P-384) و محدود کردن **CN/SAN** به یک دامنه
- Root CA آفلاین و کلید CA صادرکننده آنلاین، هر دو با رمز عبور رمزنگاری‌شده
- دانلود گواهی، زنجیره و ریشه عمومی؛ ثبت سریال/وضعیت درخواست با SQLite
- Docker Compose، محدودیت CPU/RAM، فایل‌سیستم read-only و اجرای غیر-root
- پیکربندی اختیاری Caddy برای HTTPS عمومی پنل

## نصب خودکار اولیه (macOS / Linux)

برای سروری که **Issuing CA موجود** و سه فایل PEM لازم را دارد، اجرای نصب اولیه ساده است:

```bash
git pull
python3 scripts/setup_admin.py
bash install.sh
```

اسکریپت فایل `.env` و رمزهای قبلی را حفظ می‌کند، دسترسی‌ها را بررسی می‌کند، Docker را راه‌اندازی می‌کند و `/healthz` را می‌سنجد. در نصب کاملاً جدید و **فقط روی سیستم مدیریتی امن**، ابتدا `bash install.sh --init-ca` را اجرا کنید؛ بعد از تولید CA جدید، کلید خصوصی Root را حتماً به فضای آفلاین منتقل کنید. [راهنمای کامل نصاب](docs/FIRST_RUN.md).

## نیازمندی‌ها

- سرور لینوکس با Docker Engine و Docker Compose v2؛ حدود **۴۰۰ مگابایت RAM** برای API و Caddy، به‌اضافه سربار سیستم‌عامل. اجرای API به‌تنهایی حداکثر 256MiB RAM و 0.75 CPU در Compose محدود شده است؛ این‌ها سقف منابع‌اند، نه اندازه‌گیری مصرف.
- Python 3.12+ روی سیستم مدیریت کلید برای اجرای اسکریپت اولیه، با بسته `cryptography`. بهتر است ساخت CA روی دستگاه امن و جداگانه انجام شود.
- دامنه پنل (فقط برای استفاده public) با DNS صحیح و پورت‌های ورودی 80/443 باز.

## راه‌اندازی — کلید ریشه را آفلاین نگه دارید

**۱. ساخت Root/Issuing CA روی یک سیستم مدیریتی امن، ترجیحاً نه سرور برنامه:**

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
python scripts/init_ca.py --output secrets
```

دو گذرواژه قوی و متفاوت (حداقل ۱۲ کاراکتر) تعیین کنید. اسکریپت خروجی زیر را ایجاد می‌کند و fingerprint گواهی ریشه را چاپ می‌کند:

```
secrets/
├── offline/
│   ├── root-key.pem      # SECRET - NEVER UPLOAD TO SERVER
│   └── root-cert.pem
└── online/
    ├── issuer-key.pem    # SECRET - encrypted
    ├── issuer-cert.pem
    └── root-cert.pem     # public trust anchor
```

پوشه `secrets/offline` را **فوراً از سرور اجرا جدا** کرده و در محل ایمن آفلاین با نسخه پشتیبان رمزنگاری‌شده نگه دارید. فقط `secrets/online` را به سرور منتقل کنید. ریشه عمومی را پیش از نصب در کلاینت‌ها با fingerprint چاپ‌شده از مسیر مستقل مقایسه کنید. حتی در محیط تست نیز **هیچ کلید خصوصی را در GitHub یا image Docker قرار ندهید**.

**۲. راه‌اندازی روی سرور:**

```bash
git clone https://github.com/dr-reza-khaleghifar/CA-Panel.git CA-Panel
cd CA-Panel
mkdir -p data secrets/online
# Copy ONLY the three secrets/online files from the administrative machine.
cp .env.example .env
id -u; id -g
# Edit APP_UID and APP_GID to match the owner of data/ and secrets/online/.
# Set CA_KEY_PASSWORD to the Issuing CA passphrase (NOT the root passphrase).
chmod 600 .env
# Ensure the container UID can read issuer-key.pem and write ./data.
docker compose up --build -d
curl http://127.0.0.1:8080/healthz
```

به‌صورت پیش‌فرض پنل فقط روی `127.0.0.1:8080` قابل دسترس است و مستقیماً از اینترنت منتشر نمی‌شود. از طریق SSH tunnel نیز می‌توان آن را مشاهده کرد.

**۳. HTTPS عمومی خود پنل (اختیاری):**

رکورد A/AAAA برای `PANEL_DOMAIN` را روی IP سرور تنظیم کنید. سپس `.env` را به‌روزرسانی کنید و با این دستور بالا بیاورید:

```bash
docker compose --profile public up --build -d
```

Caddy گواهی معتبر عمومی برای دامنه **پنل** می‌گیرد. وقتی تمام ترافیک اینترنت صرفاً از Caddy عبور کند، `TRUST_PROXY_HEADERS=1` را برای Rate Limit مبتنی بر IP واقعی قرار دهید و کانتینر API را به‌صورت عمومی در شبکه یا روی پورت خارجی منتشر نکنید. استفاده از API روی localhost جداگانه ممکن است هدر جعلی بپذیرد؛ پورت localhost باید فقط برای مدیر قابل دسترسی باشد. قبل از ارائه عمومی، کنترل‌های بیشتر مثل احراز هویت، سهمیه و مانیتورینگ توصیه می‌شوند.

## دریافت خودکار گواهی (صدور در سرور)

1. پنل را برای کاربران اینترنتی فقط از طریق **HTTPS** باز کنید (برای تست محلی `http://127.0.0.1:8080` مجاز است).
2. دامنه را ثبت کنید؛ برای مثال `example.org`.
3. رکورد DNS TXT را با نام `_ca-panel.example.org` و مقدار نشان‌داده‌شده منتشر کنید.
4. روی «تأیید DNS، صدور خودکار و دانلود» کلیک کنید. **خود سرور** کلید RSA با اندازه پیش‌فرض ۲۰۴۸ بیت و CSR را در حافظه می‌سازد؛ سپس پس از بررسی دوباره TXT، گواهی با اعتبار پیش‌فرض ۳۰ روزه را امضا می‌کند.
5. لینک **یک‌بارمصرف ZIP شامل کلید خصوصی** را در مهلت تنظیم‌شده (پیش‌فرض ۱۰ دقیقه) دانلود کنید؛ لینک‌های مجزای گواهی‌های عمومی هم در صفحه قابل مشاهده‌اند. فایل‌های ZIP عبارت‌اند از `example.org.key`، `example.org.crt`، `example.org-fullchain.pem`، `issuing-ca.pem`، `root-ca.pem` و `README.txt`.

ZIP رمز ندارد؛ فایل `.key` را بعد از استخراج با `chmod 600` حفاظت کنید. کلید خصوصی در سرور فقط در حافظه باقی می‌ماند و روی دیسک/SQLite ذخیره نمی‌شود؛ پس از مصرف لینک، انقضا یا راه‌اندازی مجدد امکان بازیابی وجود ندارد. **برای گواهی جدید باید درخواست DNS تازه بسازید.**

برای برنامه‌نویسان، مسیر `POST /api/requests/{id}/issue` همچنان CSR کاربر را قبول می‌کند و در آن مسیر کلید خصوصی خارج از سرور باقی می‌ماند. API صدور خودکار روی سرور: `POST /api/requests/{id}/issue-server`. تمدید خودکار زمان‌بندی‌شده هنوز پیاده‌سازی نشده است.

## توسعه و تست

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
python -m pytest -q
```

> وضعیت: **MVP محافظت‌شده**؛ ورود تک‌مدیر با MFA وجود دارد، ولی این پروژه **CA عمومی مورد اعتماد مرورگر**، RBAC چندکاربره، سامانه ACME، CRL/OCSP یا سرویس HSM نیست. برای کاربردهای حساس/گسترده نیازمند hardening و بازبینی امنیتی است.


## خطای راه‌اندازی `Incorrect password, could not decrypt key`

مقدار `CA_KEY_PASSWORD` باید **رمز Issuing CA** باشد، نه رمز Root CA. در صورت وجود کاراکتر `$` در رمز، مقدار را در `.env` داخل تک‌نقل‌قول قرار دهید تا Compose آن را تغییر ندهد. سپس `docker compose up -d --force-recreate api` را اجرا کنید. برای بررسی امن و بدون نمایش رمز، [بخش Troubleshooting در راهنمای عملیات](docs/OPERATIONS.md#startup-fails-incorrect-password-could-not-decrypt-key) را بخوانید. **کلید یا رمز را برای کسی ارسال نکنید.**


## مشکل DNS داخل Docker

اگر رکورد TXT از DNS عمومی قابل مشاهده است ولی `app.dns_debug` در Docker نتیجه `NXDOMAIN` می‌دهد، از گزینه اختیاری `DNS_RESOLVERS=1.1.1.1,1.0.0.1` در فایل `.env` استفاده کنید و کانتینر API را بازسازی کنید. تنظیم پیش‌فرض همچنان از DNS داخلی کانتینر استفاده می‌کند. [دستور تشخیص و راهنمای کامل](docs/OPERATIONS.md#docker-resolver-returns-nxdomain-but-a-public-resolver-finds-the-exact-txt).


## صدور کاملاً خودکار در سرور + لینک‌های دانلود (نسخه فعلی)

بعد از وارد کردن دامنه و تأیید TXT، پنل بدون نصب OpenSSL در دستگاه کاربر، کلید RSA (پیش‌فرض ۲۰۴۸ بیت) و گواهی را در سرور می‌سازد و لینک‌های دانلود جداگانه `.crt`, `fullchain.pem`, `issuing-ca.pem`, `root-ca.pem` و **یک ZIP حاوی کلید `.key`** ارائه می‌دهد. ZIP پیش‌فرض تا ۱۰ دقیقه قابل دانلود است، یک‌بار مصرف است و از حافظه سرور حذف می‌شود. کلید خصوصی روی دیسک یا SQLite نگهداری نمی‌شود؛ با ریستارت سرور یا گم شدن لینک باید درخواست تازه بسازید.

**امنیت:** حالا سرور در حین صدور به کلید خصوصی دسترسی دارد؛ برای کاربران اینترنتی فقط HTTPS، حفاظت از Docker و بکاپ امن را به کار بگیرید. ZIP و لینک آن محرمانه‌اند. برای کاربردهای حساس که کلید نباید در سرور CA ساخته شود، API صدور با CSR کاربر همچنان فعال است. [جزئیات API](docs/API.md) و [ملاحظات امنیتی](docs/OPERATIONS.md).


## رابط کاربری جدید (RTL و واکنش‌گرا)

رابط گواهی با طراحی داشبوردی **دارک ثابت**، پشتیبانی از موبایل و تبلت، نمایش مراحل کار، دکمه‌های کپی TXT، پیام‌های فارسی قابل فهم و جداسازی لینک ZIP خصوصی از فایل‌های گواهی عمومی بازطراحی شده است. زمان باقی‌مانده چالش DNS و لینک خصوصی نیز نشان داده می‌شود. هیچ اطلاعات محرمانه‌ای در localStorage ذخیره نمی‌شود. [مستندات UI](docs/UI.md).


## طراحی فارسی نسخه ۳

رابط فارسی با فونت [Vazirmatn](https://github.com/rastikerdar/vazirmatn) (وزیرمتن، SIL OFL 1.1)، رنگ سرمه‌ای/فیروزه‌ای، خوانایی بیشتر، تم سازمانی تیره و چیدمان موبایل به‌روزرسانی شد. فایل‌های `app/static/v3.css` و `docs/UI.md` حاوی تغییرات و راهنمای فونت هستند. برای فعال‌سازی کامل فونت، آن را یک بار روی میزبان با `python3 scripts/install_font.py` نصب کنید؛ Docker دیگر هنگام ساخت فونت دانلود نمی‌کند. این تغییر فقط UI است و منطق صدور تغییری نکرده است.

### رفع مشکل SSL دانلود فونت هنگام Docker Build

اگر ساخت Docker در `urllib.request.urlopen(...Vazirmatn...)` با `CERTIFICATE_VERIFY_FAILED` متوقف شده است، نسخه جدید دیگر در Dockerfile فونت دانلود نمی‌کند و ساخت را متوقف نخواهد کرد. برای فعال‌شدن فونت فارسی محلی، یک بار روی سیستم میزبان `python3 scripts/install_font.py` را اجرا کنید و سپس `docker compose up -d --build --force-recreate api`. اگر TLS میزبان هم معتبر نبود، از `--file` برای فایل دریافت‌شده از مسیر مطمئن استفاده کنید. **گزینه `--insecure` یا غیرفعال‌سازی بررسی SSL مجاز نیست.** [راهنمای کامل](docs/UI.md#fix-for-ssl-certificate_verify_failed-during-docker-font-download).


## خواندن اطلاعات و تنظیمات CA از `.env`
تمام تنظیمات عملیاتی از فایل `.env` توسط Docker Compose به کانتینر فرستاده می‌شوند. مقادیر نمونه و محدودیت‌ها در [`.env.example`](.env.example) هستند. شامل نام نمایشی پنل (`CA_DISPLAY_NAME`)، نام سازمان (`CA_ORGANIZATION`)، آدرس پوشه CA، نام فایل‌های PEM، اعتبار گواهی (`CERT_VALIDITY_DAYS`)، اندازه کلید RSA (`SERVER_KEY_BITS`)، مهلت DNS، محدودیت درخواست و عمر لینک ZIP است. **رمز Issuing CA** همان `CA_KEY_PASSWORD` فعلی است؛ کلیدهای خصوصی باید در فایل‌های امن، خارج از env، باقی بمانند. نام واقعی گواهی‌های Root/Issuer مستقیماً از PEM خوانده می‌شود و تغییر برچسب در .env آن‌ها را تغییر نمی‌دهد. رابط کاربری اطلاعات عمومی و اثر انگشت Root را از `GET /api/system` نمایش می‌دهد.

**برای به‌روزرسانی** بدون بازنویسی تنظیمات محرمانه موجود:
```bash
# .env فعلی را حفظ و متغیرهای دلخواه جدید را به آن اضافه کنید.
docker compose up -d --build --force-recreate api
curl http://127.0.0.1:8080/api/system
```
جزئیات: [راهنمای تنظیمات و امنیت](docs/OPERATIONS.md).


### مشخصات Root CA و Issuing CA در `.env`
برای **ساخت اولیه یک CA جدید** می‌توانید علاوه بر مسیرها و نام فایل‌ها، `CA_ROOT_CN` و `CA_ISSUER_CN` (نام واقعی داخل گواهی)، `CA_ROOT_ORGANIZATION` و `CA_ISSUER_ORGANIZATION`، مدت اعتبار `CA_ROOT_VALIDITY_DAYS` و `CA_ISSUER_VALIDITY_DAYS` و اندازه کلید `CA_ROOT_KEY_BITS` و `CA_ISSUER_KEY_BITS` را از `.env` تعیین کنید. همچنین `CA_ROOT_KEY_FILE` نام کلید آفلاین Root را مشخص می‌کند. اسکریپت‌های `bash install.sh --init-ca` و `python scripts/init_ca.py --env .env` این مقادیر را می‌خوانند. **تغییر این پارامترها بعد از ساخت CA، گواهی‌های قبلی را تغییر نمی‌دهد و باعث بازتولید کلیدها نمی‌شود.** جزئیات در [راهنمای نصب اولیه](docs/FIRST_RUN.md) و [نمونه env](.env.example) آمده است.


## اجرای HTTPS پردیس روی Firefox معمولی، بدون مرورگر اختصاصی

روی دستگاه‌های Windows/macOS/Linux تحت مدیریت می‌توانید گواهی عمومی Root CA پردیس را با **Mozilla Firefox Enterprise Policies** به Firefox عادی معرفی کنید. در Windows توزیع خودکار با GPO یا Intune امکان‌پذیر است؛ برای یک رایانه Windows اسکریپت تأییدشده `scripts/configure_firefox_trust.ps1` موجود است. هیچ سایتی نمی‌تواند به‌صورت مخفی یک Root جدید را روی دستگاه ناشناس نصب کند؛ این کار به مجوز مالک/مدیر و بررسی SHA-256 نیاز دارد.

راهنما و دستورها: [اعتماد Firefox معمولی به Root CA پردیس](docs/FIREFOX_TRUST.md).

## صدور خودکار HTTPS خود پنل بدون DNS TXT

هنگامی که Root و Issuing CA اختصاصی از قبل ساخته شده‌اند، دیگر برای **گواهی HTTPS خود پنل** نیازی به ثبت درخواست در وب‌سایت یا رکورد TXT نیست. روی همان سرور و در پوشه پروژه:

```bash
git pull
# اگر Python cryptography هنوز روی میزبان نصب نشده است:
# python3 -m venv .venv && .venv/bin/python -m pip install -r requirements.txt
bash install.sh --private-https
```

نصاب از `PANEL_DOMAIN=ca1.iravand.ir` و **کلید Issuing CA موجود در `secrets/online/`** استفاده می‌کند، یک جفت کلید/گواهی TLS تازه فقط برای همان دامنه تولید می‌کند و Caddy را روی پورت ۴۴۳ فعال می‌کند. فایل‌های TLS در `secrets/tls/` نگهداری می‌شوند؛ Issuing private key وارد کانتینر Caddy نمی‌شود.

اگر گواهی معتبر فعلی بیش از ۷ روز اعتبار داشته باشد، فایل‌ها تغییر نمی‌کنند. با اجرای دوباره همین دستور در ۷ روز پایانی، گواهی تازه جایگزین و Caddy راه‌اندازی مجدد می‌شود. **تمدید زمان‌بندی‌شدهٔ خودکار هنوز وجود ندارد**؛ برای آن لازم است اجرای دوره‌ای امن نصب‌کننده توسط مدیر تنظیم شود. این قابلیت **فقط برای نصاب محلی** است؛ تمام درخواست‌های صدور عمومی در رابط/ API همچنان نیاز به اثبات مالکیت DNS دارند. برای جزئیات [راهنمای HTTPS اختصاصی](docs/PRIVATE_HTTPS.md).

## HTTPS با گواهی اختصاصی CA سازمان روی پورت ۴۴۳

برای مسیر **دستی/اختیاری** با ZIP، مقدار `PANEL_DOMAIN=ca1.iravand.ir` را در `.env` قرار دهید، فایل ZIP گواهی همین دامنه را از پنل دریافت کنید و سپس:

```bash
python3 scripts/setup_private_tls.py --zip "$HOME/Downloads/ca1.iravand.ir-certificates.zip"
bash install.sh --private-https
```

این روش گواهی و کلید **مخصوص سایت** را در `secrets/tls/` به Caddy تحویل می‌دهد؛ کلید Issuing CA وارد وب‌سرور نمی‌شود. پروفایل `private-tls` به‌جای `public`/ACME روی ۴۴۳ استفاده می‌شود و این دو نباید هم‌زمان اجرا شوند. پیش از انتقال عمومی، اعتماد به Root CA در مرورگرهای مقصد را تنظیم کنید؛ این گواهی ذاتاً عمومی و مورد اعتماد همه مرورگرها نیست. [راهنمای کامل صدور، راه‌اندازی و تمدید HTTPS اختصاصی](docs/PRIVATE_HTTPS.md).

برای محدودکردن پورت ۴۴۳ به یک اینترفیس مشخص یا شبکه VPN، مقدار `PANEL_TLS_BIND_IP` را در `.env` تنظیم کنید (پیش‌فرض `0.0.0.0` یعنی تمام اینترفیس‌ها). دسترسی کاربران ناشناس به صفحه صدور، فقط با فعال‌کردن HTTPS محدود نمی‌شود.
